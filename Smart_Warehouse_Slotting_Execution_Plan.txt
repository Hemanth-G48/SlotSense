EXECUTION PLAN: SMART WAREHOUSE SLOTTING & OPTIMIZATION ENGINE

PURPOSE
The project is to build an end-to-end warehouse slotting system that assigns SKUs to physical storage locations while satisfying spatial, weight, safety, demand, and ergonomic constraints. It must also demonstrate measurable improvements over a baseline warehouse layout.

This plan covers the problem-solving approach, system architecture, algorithms, implementation phases, validation, and all three expected deliverables specified in the problem statement. Dataset discovery and acquisition are intentionally excluded for now.

1. DEFINE THE SOLUTION

The system should follow this pipeline:

1. Input and configuration layer
   - Warehouse topology
   - SKU metadata
   - Demand history
   - Handling rules

2. Demand and spatial analysis
   - ABC classification
   - Order affinity
   - Volume profiling
   - Accessibility scoring

3. Constraint-aware allocation engine
   - Feasible SKU-to-location assignment
   - Optimization

4. Simulation and validation
   - Baseline versus optimized layout
   - Route simulation
   - Constraint audit

5. Final outputs
   - Working prototype
   - Interactive dashboard
   - Technical documentation

Treat safety and physical feasibility as hard constraints, not as objectives that can be traded away for shorter routes. Travel distance, pick time, space utilization, and ergonomic efficiency are optimization objectives.

2. CONVERT THE PROBLEM STATEMENT INTO ENGINEERING REQUIREMENTS

Requirement: 3D spatial bounds
Implementation: Check SKU dimensions and volume against location capacity.
Evidence: No invalid dimension or volume assignments.

Requirement: Shelf and rack load limits
Implementation: Calculate cumulative assigned load at each structural level.
Evidence: Every load remains within its configured limit.

Requirement: Category and hazard compatibility
Implementation: Apply an explicit compatibility matrix.
Evidence: Zero prohibited combinations.

Requirement: Vertical placement of heavy items
Implementation: Enforce shelf-height and handling restrictions.
Evidence: No heavy SKU in prohibited upper levels.

Requirement: ABC velocity profiling
Implementation: Rank SKUs by historical demand and classify A/B/C.
Evidence: Classification table and demand distribution.

Requirement: Order affinity
Implementation: Calculate co-occurrence and association scores.
Evidence: Pair rankings and affinity clusters.

Requirement: Golden-zone placement
Implementation: Reward accessible chest-to-waist locations for frequent picks.
Evidence: Placement and ergonomic metrics.

Requirement: Baseline comparison
Implementation: Simulate identical demand against both layouts.
Evidence: Quantitative before-and-after results.

Requirement: Interactive visualization
Implementation: Display warehouse locations, routes, heatmaps and KPIs.
Evidence: Functional dashboard.

Requirement: Documentation
Implementation: Record architecture, algorithms, complexity and trade-offs.
Evidence: Technical report.

3. IMPLEMENTATION ROADMAP

PHASE 1 — FORMALIZE THE WAREHOUSE MODEL

Define the entities, constraints, configuration formats, and objective functions.

Tasks:
- Represent bins, shelves, racks, aisles, coordinates, and dispatch points.
- Represent each SKU's dimensions, weight, category, and handling requirements.
- Define shelf, rack, and location capacities, along with hazard and height restrictions.
- Define the rules for single-SKU versus mixed-SKU storage and inventory quantities.
- Specify the assignment output schema.

Output: A warehouse domain model and a formal constraint specification.

PHASE 2 — IMPLEMENT DEMAND AND AFFINITY ANALYSIS

Build analysis modules that convert transaction history into actionable placement priorities.

Tasks:
- Calculate demand frequency, quantity, and velocity for each SKU.
- Rank SKUs and classify them into ABC categories using a documented Pareto-based rule.
- Compute product co-occurrence, support, confidence, and lift, where appropriate.
- Create affinity clusters for frequently co-ordered products.
- Profile SKU volumes and identify suitable storage-capacity classes.

Output: SKU priority scores, ABC labels, affinity relationships, and volume profiles.

Dataset acquisition is deferred. Initially, modules should accept a defined input schema and use controlled test fixtures.

PHASE 3 — BUILD THE CONSTRAINT VALIDATION ENGINE

Implement a standalone validator before developing the optimizer.

Tasks:
- Verify dimensional fit, orientation, and volume feasibility.
- Enforce individual location capacity and cumulative shelf/rack weight limits.
- Reject incompatible hazardous, fragile, or restricted categories in prohibited zones.
- Enforce heavy-item shelf-height restrictions.
- Check assignment uniqueness, location availability, and inventory capacity.

Every rule should return a clear pass/fail result and a reason for failure.

Output: A reusable validation engine with automated positive and negative test cases.

PHASE 4 — DEVELOP THE ALLOCATION OPTIMIZER

The core technical challenge is finding a globally useful allocation that remains physically feasible.

Tasks:
- Generate a feasible initial allocation.
- Prioritize high-velocity SKUs for accessible locations near dispatch.
- Prefer golden-zone shelf levels for frequent picks.
- Place co-ordered products in nearby pick-faces where feasible.
- Improve the assignment using a constrained optimization algorithm.
- Revalidate every candidate solution and retain the best feasible result.

Recommended starting method: Greedy allocation with constraint checking, followed by local search or simulated annealing. For a smaller, well-defined model, use a mixed-integer linear programming (MILP) formulation.

Output: A feasible SKU-to-location mapping and an optimization log.

PHASE 5 — IMPLEMENT BASELINE AND ROUTE SIMULATION

Tasks:
- Generate a baseline layout, preferably using the actual initial layout when available; otherwise use a documented random or unoptimized allocation.
- Use the same demand scenarios and routing assumptions for both layouts.
- Simulate multi-item order picking using warehouse coordinates and aisle connectivity.
- Estimate travel distance and route completion time.
- Calculate volumetric utilization and audit safety constraints.
- Repeat randomized tests using fixed seeds when applicable.

Output: Comparable baseline and optimized results with reproducible metrics.

PHASE 6 — DEVELOP THE INTERACTIVE DASHBOARD

Tasks:
- Display warehouse racks, bays, shelf levels, and location assignments.
- Color-code locations by demand class, utilization, or safety status.
- Visualize baseline and optimized pick routes.
- Show comparative KPI cards and charts.
- Allow selection of an SKU or location to inspect its assignment and constraints.
- Provide downloadable assignment and evaluation reports.

Output: An interactive interface connected to actual allocation and simulation results.

PHASE 7 — INTEGRATION, TESTING, AND FINAL REPORTING

Tasks:
- Integrate all modules through a single execution pipeline.
- Test malformed inputs, infeasible configurations, and edge cases.
- Run end-to-end evaluations.
- Record runtime, feasibility, KPI improvements, and algorithmic limitations.
- Document architecture, complexity, and trade-offs.

Output: A reproducible end-to-end prototype, evaluation evidence, and completed technical documentation.

4. ALLOCATION ALGORITHM: THE CORE OF THE PROJECT

The main technical challenge is not merely assigning products to empty bins. It is finding an allocation that remains physically feasible and improves warehouse operations.

4.1 Define the decision variables

Let:
- i represent a SKU.
- j represent a storage location.
- x_ij = 1 if SKU i is assigned to location j, and 0 otherwise.
- d_i represent the demand or pick frequency of SKU i.
- c_j represent the travel cost of accessing location j.

For a single-location-per-SKU model, assignment uniqueness is:

    sum over j of x_ij = 1, for every SKU i

An assignment is permitted only if the SKU is compatible with the location. Define a_ij = 1 for compatible pairs and 0 otherwise:

    x_ij <= a_ij

Location capacity, structural load, and compatibility constraints must also be enforced. If multiple SKUs or inventory units may share a location, extend the model to represent quantities and occupancy explicitly.

4.2 Define the optimization objectives

A practical starting objective is to minimize weighted picking cost:

    minimize sum over i and j of d_i * c_j * x_ij

This encourages frequently picked items to occupy accessible locations. However, this objective alone does not account for every requirement.

The full model should also account for:
- Order affinity: Reduce separation between frequently co-ordered SKUs.
- Ergonomics: Prefer suitable picking heights for frequent picks and safe heights for heavy items.
- Space utilization: Match SKU dimensions and inventory requirements to available storage capacity.
- Travel time: Account for aisle connectivity, turns, congestion assumptions, and handling time where modeled.

One implementation is a weighted objective:

    minimize alpha*D + beta*A + gamma*E + delta*U

Where:
- D = travel cost
- A = affinity penalty
- E = ergonomic penalty
- U = space-utilization penalty
- alpha, beta, gamma, delta = documented weights

The weights must be documented and calibrated. Safety rules should not be softened by objective weights; they must be enforced as hard constraints.

4.3 Choose the optimization strategy

Greedy allocation:
- Advantages: Simple, fast, easy to explain.
- Limitations: Can miss better global assignments.
- Role: Initial feasible solution.

Local search:
- Advantages: Improves an existing assignment through swaps and moves.
- Limitations: May get trapped in local optima.
- Role: Primary refinement method.

Simulated annealing:
- Advantages: Can escape some local optima.
- Limitations: Requires parameter tuning.
- Role: Larger or more complex layouts.

Mixed-integer linear programming (MILP):
- Advantages: Explicit mathematical formulation and solver-based guarantees within solver limits.
- Limitations: May become computationally expensive.
- Role: Small/medium instances or benchmark.

Hybrid approach:
- Advantages: Combines speed with iterative improvement.
- Limitations: More engineering effort.
- Role: Recommended final prototype.

Recommendation: Start with greedy allocation, local search, and strict validation. If time permits, compare against a MILP solution on a smaller test instance to assess solution quality.

The final algorithm should report whether it found a feasible solution, whether it reached its stopping criterion, and how long it took. Do not label a heuristic solution globally optimal unless that is actually established.

5. DESIGN THE BASELINE-VERSUS-OPTIMIZED EVALUATION

The problem statement explicitly requires quantitative proof of improvement. A visually better layout is not sufficient.

Required metrics

1. Total pick travel distance
   Calculation: Sum of route distances across evaluated orders.
   Interpretation: Lower is better.

2. Pick route completion time
   Calculation: Travel time plus modeled handling and other included delays.
   Interpretation: Lower is better.

3. Volumetric cube utilization
   Calculation: Occupied volume / usable storage volume * 100.
   Interpretation: Higher may be better.

4. Safety compliance
   Calculation: Number of violations against enforced rules.
   Requirement: Must be zero for the optimized layout.

5. Assignment feasibility
   Calculation: Number of valid assignments / total assignments * 100.
   Requirement: Must be 100%.

6. Optimization runtime
   Calculation: Wall-clock execution time.
   Interpretation: Measures practical usability.

Travel distance reduction:

    Reduction (%) =
      (Baseline distance - Optimized distance) / Baseline distance * 100

Utilization improvement:

    Delta utilization = Optimized utilization - Baseline utilization

Report utilization changes in percentage points, separately from relative percentage improvement.

Evaluation rules:
- Use identical orders, SKU quantities, warehouse geometry, and route-planning assumptions for both layouts.
- Use the same routing algorithm for both configurations.
- Validate the baseline as well as the optimized layout. If the baseline contains violations, report them instead of silently correcting them.
- Report raw baseline values, optimized values, absolute differences, and percentage changes.
- Test whether results are stable across different order mixes or random seeds.
- Record infeasibility and runtime failures rather than excluding them without explanation.

7. EXPECTED DELIVERABLES

DELIVERABLE 1 — WORKING ALLOCATION PROTOTYPE

Primary artifact: Executable software.

It should accept warehouse configurations, SKU metadata, and demand inputs; execute allocation; enforce all hard constraints; and produce a feasible storage assignment.

Required output files should include:
- optimized_assignments.csv — SKU-to-location mapping.
- constraint_audit.csv — rule checks and violations.
- optimization_summary.json — objective values, runtime, and run status.
- baseline_assignments.csv — baseline mapping used for evaluation.

Acceptance test: The program runs end to end and either returns a verified feasible solution or explicitly reports that no feasible solution was found.

DELIVERABLE 2 — INTERACTIVE OPTIMIZATION DASHBOARD

Primary artifact: Demonstrable user interface.

It should include:
- A warehouse grid or layout visualization.
- Location-level assignment, utilization, and demand-class views.
- Baseline versus optimized route visualization.
- KPI comparisons for distance, time, utilization, and safety.
- SKU/location inspection and constraint-violation details.
- Export functionality for results.

Acceptance test: Changing the input configuration or selecting a completed optimization run updates the displayed results from the underlying data, not hardcoded example charts.

DELIVERABLE 3 — TECHNICAL AND ALGORITHMIC DOCUMENTATION

Primary artifact: Technical report.

Include:
- Problem formulation, assumptions, and scope.
- System architecture and data flow.
- Input/output schemas.
- Spatial, structural, and safety constraint logic.
- ABC and affinity-analysis methods.
- Optimization algorithm and objective functions.
- Computational complexity and scalability discussion.
- Baseline/optimized evaluation methodology and actual results.
- EDA findings once the dataset phase is undertaken.
- Trade-off analysis, limitations, and future improvements.

Acceptance test: Another developer can understand the model, reproduce an evaluation, and interpret the reported performance without relying on undocumented assumptions.

9. RECOMMENDED ORDER OF EXECUTION

1. Formalize the warehouse model and hard constraints.
2. Implement the validator and test it independently.
3. Build demand, ABC, affinity, and volume-analysis modules.
4. Create a feasible initial allocation and improve it with a constrained optimizer.
5. Implement a consistent route simulator and baseline comparison.
6. Build the interactive dashboard around actual engine outputs.
7. Complete end-to-end testing and technical documentation.
8. Integrate the dataset pipeline later, without changing the architecture unnecessarily.

MOST IMPORTANT DESIGN DECISION

Build the constraint validator and evaluation framework before spending time on advanced optimization or dashboard styling. Without them, the system may produce attractive layouts without proving that the assignments are safe, feasible, or genuinely more efficient.
