# PHASE 2 — Dataset Pipeline & Exploratory Data Analysis (EDA)

## Goal
Build a complete, self-consistent dataset that the engine can run on, plus a documented EDA.
The problem statement provides no ready-made dataset, so you must curate and/or synthesize one with
clear provenance. Keep the raw source untouched and separate from processed/cleaned data.

## Context you need
- Read `warehouse_optimization_dataset_roadmap.txt` in full — it is the authoritative plan for this
  phase (10 phases of data construction). Follow its canonical tables, units, validation rules, and
  reproducibility requirements.
- Use the `src/models/` schema from Phase 1 as the target/output schema.
- For EDA methodology, reference `useful_repos/Warehouse-Order-Picking-Operational-Analytics`
  (ABC, travel-distance, slotting-policy analysis).

## Tasks

### 1. Define the dataset architecture
Create the table/relationship design (per roadmap Phase 1):
`products`, `categories`, `orders`, `order_items`, `warehouses`, `locations`, `inventory`,
`compatibility_rules`, `storage_assignments` (baseline + optimized, kept separate),
`location_graph`. Add `data_source` and `data_quality_status` fields so measured / sourced /
inferred / synthetic values are distinguishable.

### 2. Optionally acquire real source data (clearly labeled)
Open-data candidates that map into your schema (check licensing before redistributing):
- Mendeley **Footwear Warehouse** dataset (real operations, SKUs, storage locations, coords).
- **Instacart Market Basket**, **Kaggle Online Retail II**, or **Olist Brazilian E-Commerce**
  (order/demand data).
- University of Hamburg **Artificial Order Picking** data (synthetic, keep provenance).
Preserve originals in a `raw/` directory; only bring them in if they actually map to your schema
(e.g., don't pretend footwear data contains dimensions/weights it doesn't have).

### 3. Generate the primary synthetic benchmark dataset
Because real data rarely covers all required attributes, build a **generalized synthetic
warehouse** as the main controlled benchmark. Make it reproducible with a fixed seed.

- **Diverse SKU master** (1,000–3,000 SKUs, 8–12 categories) with physically plausible
  dimensions/weights generated by product class (see roadmap Phase 4 for the mix and the
  "don't independently randomize dimensions" guidance). Record the generation method.
- **Warehouse topology** (500–2,500 locations) from your Phase 1 geometry generator:
  zones, aisles, racks, bays, shelves, bins with capacities, ergonomic zones, coordinates.
  Derive a distance graph from the layout (locations + dispatch → nodes; aisle connectivity →
  edges weighted by distance).
- **Order history** (20,000–100,000 order lines) over the unified SKU master. Generate at least
  **three demand scenarios**:
  - Scenario A: strongly concentrated demand (tests ABC / fast-mover placement).
  - Scenario B: broad, balanced demand (tests general slotting).
  - Scenario C: strong product co-occurrence (tests affinity grouping and multi-item routes).
  Document how demand frequencies and associations are generated (e.g., Zipf/power-law skew).
- **Inventory**, **compatibility rules**, and a **feasible baseline assignment**.

### 4. Clean, standardize, and validate
- Build clean_data / validate scripts. Reject or flag (don't silently delete) records with:
  missing IDs, zero/negative dimensions or weights, negative quantities, duplicate unaggregated
  order-items, invalid timestamps, duplicate location IDs, references to nonexistent SKUs/locations.
- Verify referential integrity, physical plausibility, geometric consistency, and that the
  optimizer's baseline is feasible (or explicitly flagged if not).

### 5. Exploratory Data Analysis (mandatory, documented)
Produce an EDA report covering:
- **Demand velocity profiling**: Pareto (80/20) analysis → Class A/B/C tiers with a cumulative
  share curve. Use documented thresholds (e.g., A = first 80% of cumulative demand, B = next 15%,
  C = remaining 5%). Document the aggregation (frequency vs. units vs. picked units).
- **Affinity & co-occurrence matrix**: market-basket analysis (Apriori or association scoring) →
  support, confidence, lift for SKU pairs; identify co-order clusters.
- **Volumetric density & space profiling**: product volume distributions vs. bin capacity classes;
  surface underutilization, volume-mismatch bottlenecks, and density opportunities.
- Visualize each finding (charts saved for the dashboard and documentation).

## Deliverables / outputs for this phase
- `data/raw/` (unchanged originals, if any) and `data/processed/` (clean tables: products,
  categories, orders, order_items, locations, inventory, compatibility_rules, baseline_assignments,
  location_graph).
- Generation + cleaning + validation scripts (seeded, recorded).
- A `data/metadata/` source manifest + data dictionary (field meanings, units, provenance).
- EDA report with charts (PDF/HTML) summarizing velocity, affinity, and space findings.

## Acceptance checks (verify before finishing)
- [ ] All tables have consistent units and unique keys; errors logged, not silently dropped.
- [ ] Referential integrity passes (every order_item → existing order & SKU; every assignment →
  existing location).
- [ ] Reproducible: same seed → same dataset.
- [ ] ABC, affinity, and space profiling are implemented and documented.
- [ ] Three demand scenarios exist and are clearly labeled.
- [ ] Baseline assignments are physically feasible (or deliberately-flagged violations).

## Constraints / gotchas
- Do NOT merge unrelated datasets as if their IDs refer to the same products; use an ID-mapping
  table and only merge with supporting evidence.
- Distinguish measured / sourced / inferred / synthetic provenance on every field.
- Do not use product names or popularity as a substitute for physical dimensions.
- Keep baseline assignments immutable for the evaluation phases.
